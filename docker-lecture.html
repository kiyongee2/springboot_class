1 도커란 무엇인가

🎯 학습목표
  • 도커가 해결하는 문제("내 PC에서는 되는데…")를 설명할 수 있다.
  • 가상머신(VM)과 컨테이너의 차이를 구분할 수 있다.

📖 왜 도커가 필요할까?

블로그 프로젝트를 친구 PC나 서버에서 실행하려면 Java 21, MySQL, 환경변수, 포트 설정 등을 똑같이 맞춰야 합니다. 하나라도 다르면 "내 PC에서는 되는데 서버에서는 안 돼요"가 생깁니다.

도커(Docker)는 프로그램과 그 프로그램이 돌아가는 데 필요한 모든 것(런타임, 라이브러리, 설정)을 하나의 상자(컨테이너)로 묶어서, 어디서든 똑같이 실행되게 해 주는 도구입니다.

💡 비유: 화물 컨테이너
배에 싣는 화물 컨테이너는 안에 무엇이 들었든 크기와 규격이 같아서 배·트럭·기차 어디에나 그대로 실을 수 있습니다. 도커 컨테이너도 마찬가지로, 안에 Spring Boot가 있든 MySQL이 있든 도커만 설치되어 있으면 Windows·Mac·Linux 서버 어디서나 같은 방식으로 실행됩니다.

3 설치와 첫 실행

🎯 학습목표
  • Windows에 Docker Desktop을 설치하고 동작을 확인할 수 있다.

① Docker Desktop 설치 (Windows)

  1. docker.com에서 Docker Desktop for Windows를 내려받아 설치합니다.
  2. 설치 중 "Use WSL 2 instead of Hyper-V"를 선택합니다. (WSL 2가 없으면 관리자 PowerShell에서 wsl --install 후 재부팅)
  3. 설치 후 Docker Desktop을 실행하고, 왼쪽 아래 상태가 Engine running(초록색)인지 확인합니다.

② 설치 확인

PowerShell
docker --version
docker run hello-world

hello-world를 실행하면 도커가 다음 순서로 동작합니다.

내 PC에 이미지 있나?→ 없음 →Docker Hub에서 pull→컨테이너 생성·실행→"Hello from Docker!" 출력 후 종료
💡 Tip
명령을 입력했는데 error during connect ... pipe/docker_engine이 나오면 Docker Desktop이 꺼져 있는 것입니다. 먼저 Docker Desktop을 실행하세요.

5 실습: 도커로 MySQL 사용하기

🎯 학습목표
  • MySQL을 PC에 직접 설치하지 않고 도커 컨테이너로 실행할 수 있다.
  • 컨테이너에 접속해 SQL을 실행하고, 볼륨으로 데이터가 유지되는 것을 확인할 수 있다.
💡 도커로 DB를 쓰면 좋은 점
  • 설치 프로그램, 서비스 등록, 삭제 후 남는 찌꺼기가 없습니다.
  • MySQL 8.0, 8.4처럼 여러 버전을 동시에 띄울 수 있습니다. (포트만 다르게)
  • 팀원 모두가 같은 명령 한 줄로 같은 DB 환경을 만듭니다.

5-1. MySQL 컨테이너 실행

PowerShell (줄바꿈 기호: 백틱 `)
docker run -d `
  --name mysql-blog `
  -p 3306:3306 `
  -e MYSQL_ROOT_PASSWORD=root1234 `
  -e MYSQL_DATABASE=blogdb `
  -e MYSQL_USER=blog `
  -e MYSQL_PASSWORD=blog1234 `
  -e TZ=Asia/Seoul `
  -v mysql-data:/var/lib/mysql `
  mysql:8.4 `
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
한 줄 버전 (cmd · PowerShell · Mac/Linux 공통)
docker run -d --name mysql-blog -p 3306:3306 -e MYSQL_ROOT_PASSWORD=root1234 -e MYSQL_DATABASE=blogdb -e MYSQL_USER=blog -e MYSQL_PASSWORD=blog1234 -e TZ=Asia/Seoul -v mysql-data:/var/lib/mysql mysql:8.4 --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
부분의미
-p 3306:3306내 PC의 3306 포트로 들어온 요청을 컨테이너의 3306(MySQL)으로 전달
MYSQL_ROOT_PASSWORDroot 비밀번호 (필수, 없으면 컨테이너가 바로 종료됨)
MYSQL_DATABASE처음 시작할 때 blogdb 데이터베이스를 자동 생성
MYSQL_USER / MYSQL_PASSWORD앱에서 쓸 일반 계정 생성. 이 계정은 blogdb에 모든 권한을 가짐
-v mysql-data:/var/lib/mysqlMySQL 데이터 폴더를 mysql-data 볼륨에 저장 → 컨테이너를 지워도 데이터 유지
mysql:8.4Docker Hub 공식 MySQL 이미지, 8.4(LTS) 버전
--character-set-server=...이미지 이름 뒤에 쓰는 값은 MySQL 서버에 전달됨. 한글·이모지 저장을 위해 utf8mb4 지정
🚨 포트 충돌 주의
PC에 MySQL이 이미 설치되어 실행 중이면 3306 포트를 쓰고 있어서 port is already allocated 오류가 납니다. 이때는 -p 3307:3306처럼 왼쪽(호스트) 포트만 바꾸고, 접속할 때 3307을 사용합니다.

5-2. 실행 확인

PowerShell
docker ps                      # STATUS가 Up 이면 실행 중
docker logs -f mysql-blog      # "ready for connections" 가 보이면 접속 가능 (Ctrl+C로 나오기)
💡 Tip
처음 실행할 때는 DB 초기화 때문에 10~30초 정도 걸립니다. 로그에 ready for connections가 나오기 전에 접속하면 실패할 수 있습니다.

5-3. 컨테이너 안에서 SQL 실행

PowerShell
docker exec -it mysql-blog mysql -u blog -p
# Enter password: blog1234 입력 (화면에 표시되지 않음)
mysql>
SHOW DATABASES;
USE blogdb;

CREATE TABLE memo (
  id      BIGINT AUTO_INCREMENT PRIMARY KEY,
  content VARCHAR(200),
  created DATETIME DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO memo (content) VALUES ('도커로 띄운 MySQL 😀');
SELECT * FROM memo;
EXIT;

DBeaver, MySQL Workbench, IntelliJ Database 창으로도 접속할 수 있습니다.

항목값
Hostlocalhost
Port3306 (포트를 바꿨다면 3307)
Databaseblogdb
User / Passwordblog / blog1234
드라이버 속성allowPublicKeyRetrieval=true, useSSL=false (Public Key Retrieval 오류가 날 때)

5-4. 볼륨으로 데이터가 유지되는지 확인

PowerShell
# ① 컨테이너를 완전히 삭제
docker rm -f mysql-blog

# ② 같은 볼륨(mysql-data)을 연결해 다시 실행 (5-1 명령 그대로)
docker run -d --name mysql-blog -p 3306:3306 -e MYSQL_ROOT_PASSWORD=root1234 -e TZ=Asia/Seoul -v mysql-data:/var/lib/mysql mysql:8.4

# ③ 데이터가 남아 있는지 확인
docker exec -it mysql-blog mysql -u blog -pblog1234 blogdb -e "SELECT * FROM memo;"

memo 데이터가 그대로 보이면 성공입니다. 데이터는 컨테이너가 아니라 볼륨에 저장되어 있기 때문입니다.

💡 볼륨 관련 명령
docker volume ls (목록) · docker volume inspect mysql-data (상세) · docker volume rm mysql-data (삭제 — DB 데이터가 영구 삭제되니 주의)
※ MYSQL_DATABASE, MYSQL_USER 같은 초기화 환경변수는 볼륨이 비어 있을 때 처음 한 번만 적용됩니다. 비밀번호를 바꾸려고 환경변수만 고쳐도 기존 볼륨에는 반영되지 않습니다.

6 Spring Boot와 MySQL 컨테이너 연결

🎯 학습목표
  • 블로그 프로젝트를 H2 대신 도커 MySQL에 연결해 실행할 수 있다.

블로그 프로젝트에는 이미 runtimeOnly 'com.mysql:mysql-connector-j'가 build.gradle에 있으므로 드라이버는 추가할 필요가 없습니다. 로컬 도커 MySQL용 프로파일 파일만 하나 만듭니다.

src/main/resources/application-docker.yaml
# 로컬 도커 MySQL 전용 설정 (실행 시 프로파일 docker 활성화)
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/blogdb?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8
    username: blog
    password: blog1234
    driver-class-name: com.mysql.cj.jdbc.Driver
  jpa:
    hibernate:
      ddl-auto: update          # 재시작해도 테이블·데이터 유지
    show-sql: true
  sql:
    init:
      mode: never               # H2용 data.sql은 실행하지 않음
  h2:
    console:
      enabled: false

실행 방법

  • IntelliJ: Run → Edit Configurations → Active profiles에 docker 입력, Environment variables에 GEMINI_API_KEY=...
  • 터미널: 
    $env:GEMINI_API_KEY="발급받은키"
./gradlew bootRun --args='--spring.profiles.active=docker'

앱 실행 후 docker exec -it mysql-blog mysql -u blog -pblog1234 blogdb -e "SHOW TABLES;"로 JPA가 만든 테이블(article, users 등)을 확인합니다.

💡 기존 prod 프로파일과 비교
application-prod.yaml(AWS RDS용)은 ${RDS_HOSTNAME} 같은 환경변수로 접속 정보를 받습니다. 도커 MySQL도 결국 "주소만 다른 MySQL"이므로, 연결 방식은 완전히 같습니다. 바뀌는 것은 호스트·포트·계정뿐입니다.

7 Docker Compose — 여러 컨테이너를 한 번에

🎯 학습목표
  • 긴 docker run 명령을 compose.yaml 파일로 관리할 수 있다.
  • 컨테이너끼리 서비스 이름으로 통신한다는 것을 이해한다.

5단원의 긴 명령을 매번 치기는 번거롭습니다. Docker Compose는 컨테이너 설정을 YAML 파일에 적어 두고 docker compose up 한 번으로 실행하게 해 줍니다. Docker Desktop에 기본 포함되어 있습니다.

7-1. MySQL만 Compose로

compose.yaml (프로젝트 루트)
services:
  db:
    image: mysql:8.4
    container_name: mysql-blog
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root1234
      MYSQL_DATABASE: blogdb
      MYSQL_USER: blog
      MYSQL_PASSWORD: blog1234
      TZ: Asia/Seoul
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:                   # DB가 실제로 접속 가능한지 주기적으로 검사
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10

volumes:
  mysql-data:
명령어설명
docker compose up -d파일에 적힌 서비스 모두 실행
docker compose ps상태 확인 (healthy 표시)
docker compose logs -f dbdb 서비스 로그
docker compose down컨테이너 중지·삭제 (볼륨은 유지)
docker compose down -v볼륨까지 삭제 → DB 초기화
💡
5단원에서 docker run으로 만든 mysql-blog 컨테이너가 남아 있으면 이름이 겹쳐 오류가 납니다. 먼저 docker rm -f mysql-blog로 지우세요.

7-2. 블로그 앱 + MySQL 함께 실행

8단원의 Dockerfile이 있으면 앱도 컨테이너로 만들어 DB와 함께 띄울 수 있습니다.

compose.yaml (db 아래에 app 서비스 추가)
  app:
    build: .                       # 현재 폴더의 Dockerfile로 이미지 빌드
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: render
      DB_URL: jdbc:mysql://db:3306/blogdb?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8
      DB_USERNAME: blog
      DB_PASSWORD: blog1234
      GEMINI_API_KEY: ${GEMINI_API_KEY}   # PC의 환경변수 또는 .env 파일 값
    depends_on:
      db:
        condition: service_healthy   # DB가 healthy가 된 뒤에 앱 시작
🚨 가장 많이 틀리는 부분: localhost가 아니라 db
컨테이너 안에서 localhost는 그 컨테이너 자신을 뜻합니다. app 컨테이너 안에는 MySQL이 없으므로 localhost:3306으로는 접속할 수 없습니다. Compose는 서비스들을 같은 네트워크로 묶고 서비스 이름(db)을 호스트 이름으로 쓸 수 있게 해 줍니다.

Compose 안의 app 컨테이너db:3306

SPRING_PROFILES_ACTIVE: render는 3강 5단원에서 만든 application-render.yaml(접속 정보를 DB_URL·DB_USERNAME·DB_PASSWORD 환경변수로 받는 파일)을 그대로 재사용한다는 뜻입니다. Render 배포 전에 내 PC에서 운영과 같은 구성으로 미리 테스트할 수 있습니다.

🎯 학습목표

  • 만든 이미지를 내 PC에서 직접 빌드·실행해 볼 수 있다.

8-2. 멀티 스테이지 빌드란?

이 Dockerfile에는 FROM이 두 번 나옵니다. 첫 번째 단계에서 jar를 만들고, 두 번째 단계에서는 만들어진 jar만 가져와 새 이미지를 만듭니다. 첫 번째 단계의 소스 코드, Gradle 캐시, JDK는 최종 이미지에 들어가지 않습니다.

① build 단계 (eclipse-temurin:21-jdk)소스 코드 전체
Gradle + 의존성 라이브러리

→ build/libs/blog-0.0.1-SNAPSHOT.jar
➜
jar만
복사
② 실행 단계 (eclipse-temurin:21-jre)JRE(실행만 가능)

→ 최종 이미지 (작고 안전)

이미지 크기JDK + 소스 + Gradle 캐시까지 포함 → 큼JRE + jar만 → 작음
보안소스 코드가 이미지에 그대로 남음소스 코드가 없음
배포 속도업로드·다운로드 느림빠름
💡 JDK vs JRE
JDK(Java Development Kit)는 컴파일러(javac)를 포함한 개발 도구 세트이고, JRE(Java Runtime Environment)는 이미 만들어진 프로그램을 실행만 하는 환경입니다. 빌드에는 JDK, 실행에는 JRE면 충분합니다.

8-3. 한 줄씩 해설

코드설명
FROM eclipse-temurin:21-jdk AS buildEclipse 재단이 배포하는 OpenJDK 21 이미지에서 시작. AS build로 이 단계에 이름을 붙여 뒤에서 --from=build로 참조. 프로젝트의 languageVersion = 21과 버전을 맞춤
WORKDIR /app컨테이너 안 작업 폴더를 /app으로 지정(없으면 생성). 이후 명령은 이 폴더에서 실행 — cd /app과 같은 효과
COPY . .앞의 . = 내 PC의 현재 폴더(빌드 컨텍스트), 뒤의 . = 컨테이너의 /app. 프로젝트 전체를 복사하되 .dockerignore에 적힌 것은 제외
RUN chmod +x gradlewWindows에서 만든 gradlew 파일은 리눅스 실행 권한이 없을 수 있어 Permission denied가 남. 실행 권한 부여
./gradlew clean bootJar이전 빌드 결과를 지우고, 내장 톰캣이 포함된 실행 가능한 jar를 build/libs/에 생성
-x test테스트 단계 제외(exclude). 테스트가 DB·API 키 등을 필요로 하면 빌드 중 실패할 수 있기 때문. 테스트는 배포 전에 로컬에서 따로 실행
--no-daemonGradle 데몬(백그라운드 프로세스)을 띄우지 않음. 한 번 빌드하고 끝나는 컨테이너에서는 데몬이 메모리만 차지
FROM eclipse-temurin:21-jre두 번째 단계 시작. 앞 단계 내용은 모두 버리고 실행 전용 JRE 이미지에서 새로 시작
COPY --from=build /app/build/libs/*.jar app.jarbuild 단계의 결과물 중 jar만 가져와 app.jar로 이름을 바꿔 저장. 버전이 바뀌어도(blog-0.0.2.jar) 실행 명령을 고칠 필요가 없음
ENV JAVA_OPTS="-Xmx300m"환경변수 기본값 설정. 자바 힙 최대 크기를 300MB로 제한 → Render 무료 인스턴스(512MB RAM)에서 메모리 초과로 종료되는 것을 방지. 실행 시 -e JAVA_OPTS=...로 덮어쓸 수 있음
EXPOSE 8080"이 컨테이너는 8080 포트를 사용한다"는 문서 역할. 실제로 포트를 여는 것은 docker run -p
ENTRYPOINT [...]컨테이너가 시작될 때 실행할 명령. 아래 8-4 참고

8-4. ENTRYPOINT를 자세히

ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -Dserver.port=${PORT:-8080} -jar app.jar"]
  • 왜 sh -c로 감쌌나? — ["java", "$JAVA_OPTS", ...]처럼 쓰면 도커는 셸 없이 바로 java를 실행하므로 $JAVA_OPTS가 글자 그대로 전달됩니다. sh -c로 셸을 거쳐야 환경변수가 실제 값으로 바뀝니다.
  • ${PORT:-8080} — 셸 문법으로 "PORT 환경변수가 있으면 그 값, 없으면 8080". Render는 앱이 사용할 포트를 PORT 환경변수로 알려 줍니다. 로컬에서는 PORT가 없으니 8080으로 실행됩니다.
  • -Dserver.port=... — 자바 시스템 속성으로 Spring Boot의 server.port를 지정. application.yaml의 값보다 우선합니다.
💡 실제로 실행되는 명령
환경최종 명령
로컬 (PORT 없음)java -Xmx300m -Dserver.port=8080 -jar app.jar
Render (PORT=10000일 때)java -Xmx300m -Dserver.port=10000 -jar app.jar

8-5. .dockerignore

COPY . .로 복사할 때 빼야 할 파일 목록입니다. .gitignore와 문법이 같습니다.

항목제외하는 이유
build/, out/로컬 빌드 결과물. 컨테이너 안에서 새로 빌드하므로 불필요하고, 남아 있으면 *.jar가 여러 개 잡혀 혼란
.gradle/로컬 Gradle 캐시. 용량이 크고 OS마다 달라 오히려 문제를 일으킴
.idea/, *.imlIntelliJ 설정 파일. 실행과 무관
uploads/로컬에서 업로드한 테스트 이미지. 이미지에 넣을 필요 없음
💡 추가하면 좋은 항목
.git/(커밋 기록, 용량 큼), .env(비밀번호·API 키가 이미지에 들어가지 않도록)

8-6. 내 PC에서 빌드·실행해 보기

PowerShell (Dockerfile이 있는 프로젝트 폴더에서)
# ① 이미지 빌드 (-t: 이름:태그, 마지막 . = 빌드 컨텍스트)
docker build -t blog-app:1.0 .

# ② 이미지 확인 (JRE 기반이라 JDK 이미지보다 훨씬 작음)
docker images blog-app

# ③ H2(기본 프로파일)로 실행 — DB 없이 바로 확인
docker run --rm -p 8080:8080 -e GEMINI_API_KEY=발급받은키 blog-app:1.0

# ④ PORT 환경변수 동작 확인 — 컨테이너는 9000, 내 PC는 8081
docker run --rm -p 8081:9000 -e PORT=9000 -e GEMINI_API_KEY=발급받은키 blog-app:1.0

③은 http://localhost:8080, ④는 http://localhost:8081로 접속합니다. 로그에 Tomcat started on port 9000이 보이면 ${PORT:-8080}이 제대로 동작한 것입니다.

🚨 GEMINI_API_KEY를 빠뜨리면
application.yaml에 api-key: ${GEMINI_API_KEY}가 있어서, 값이 없으면 앱이 시작하지 못하고 Could not resolve placeholder 'GEMINI_API_KEY' 오류로 종료됩니다. 도커 이미지에는 키를 넣지 않고, 실행할 때 -e로 주입하는 것이 원칙입니다.

8-7. 한 단계 더: 빌드 캐시 활용

도커는 Dockerfile의 각 줄을 레이어로 저장하고, 내용이 바뀌지 않은 줄은 다시 실행하지 않습니다(캐시). 지금 Dockerfile은 COPY . .로 전부 복사하므로, Java 파일 한 줄만 고쳐도 의존성 다운로드부터 전부 다시 합니다. 다음처럼 바꾸면 build.gradle이 바뀌지 않는 한 의존성 다운로드를 건너뜁니다.

Dockerfile — build 단계 개선판
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
# 1) 자주 안 바뀌는 빌드 설정 파일만 먼저 복사 → 의존성 다운로드 (캐시됨)
COPY gradlew settings.gradle build.gradle ./
COPY gradle gradle
RUN chmod +x gradlew && ./gradlew dependencies --no-daemon
# 2) 자주 바뀌는 소스 코드는 나중에 복사
COPY src src
RUN ./gradlew bootJar -x test --no-daemon

실행 단계(두 번째 FROM 이하)는 그대로 둡니다. 두 번째 빌드부터 시간이 눈에 띄게 줄어듭니다.
