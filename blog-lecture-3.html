1 Spring Security — 개념 이해

🎯 학습목표
  • 인증(Authentication)과 인가(Authorization)의 차이를 비유로 설명할 수 있다.
  • 시큐리티 필터 체인이 컨트롤러 앞에서 요청을 검사하는 구조를 이해한다.
  • UserDetails / UserDetailsService / PasswordEncoder의 역할을 구분할 수 있다.
  • SecurityFilterChain으로 URL별 출입 규칙을 정하는 방법과 로그인 처리 흐름을 설명할 수 있다.

1-1. 스프링 시큐리티 한눈에 보기

📖 인증과 인가 — 회사 출입에 비유하면

구분질문회사 비유블로그에서는
인증
Authentication		“너 누구야?”출입문에서 사원증 · RFID를 찍어 신원 확인이메일 + 비밀번호로 로그인
인가
Authorization		“너 이거 해도 돼?”직급 · 직무에 따라 들어갈 수 있는 방이 다름로그인한 사람만 글 목록 · 작성 가능 (ADMIN만 관리 페이지 등)
💡 핵심 한 줄 시큐리티는 컨트롤러보다 먼저 동작합니다. 그래서 로그인 POST(/login)나 권한 검사 코드를 컨트롤러에 직접 만들지 않고, 설정(SecurityConfig)으로 규칙만 알려 주면 됩니다.

📖 아무 설정 없이 실행하면?

시큐리티 스타터를 추가하고 실행하면 모든 URL이 잠기고 기본 로그인 폼(/login)으로 이동합니다. 아이디는 user, 비밀번호는 실행할 때마다 콘솔에 새로 찍힙니다. “경비실이 생겼는데 아직 출입 명단이 없는 상태”입니다.

📌 참고 SecurityFilterChain 빈을 직접 등록하면 이 기본 설정은 꺼지고, 우리가 작성한 규칙이 적용됩니다. 규칙 없이 return http.build();만 하면 오히려 모두 통과됩니다.

📖 공식 가이드 — Securing a Web Application

spring.io → Projects → Spring Security → LEARN 탭 → Guides의 “Securing a Web Application”에서 지금 배우는 흐름(기본 로그인 → SecurityFilterChain → In-Memory 사용자)을 그대로 따라 해 볼 수 있습니다. 가이드는 항상 최신 버전(현재 Spring Security 7.1.2) 기준으로 작성됩니다.

💡 공식 가이드의 WebSecurityConfig.java (Spring Security 7.1.2)
@Configuration
@EnableWebSecurity
class WebSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) {
        http
            .authorizeHttpRequests((requests) -> requests
                .requestMatchers("/", "/home").permitAll()   // 누구나
                .anyRequest().authenticated()                // 나머지는 로그인 필요
            )
            .formLogin((form) -> form
                .loginPage("/login")                         // 사용자 정의 로그인 화면
                .permitAll()
            )
            .logout(LogoutConfigurer::permitAll);            // 로그아웃 누구나 허용

        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    UserDetailsService userDetailsService(PasswordEncoder encoder) {
        String password = encoder.encode("password");
        UserDetails user = User.withUsername("user").password(password).roles("USER").build();
        return new InMemoryUserDetailsManager(user);
    }
}
📌 가이드 코드에서 눈여겨볼 점 ① Security 7에서는 securityFilterChain(HttpSecurity http)에 throws Exception이 없어도 됩니다. (붙여도 동작은 같음)
② PasswordEncoder를 메서드 파라미터로 주입받아 사용합니다. 블로그의 UserService처럼 생성자로 주입받아도 결과는 같습니다.
③ InMemoryUserDetailsManager는 DB 없이 메모리에 사용자를 두는 연습용 방식입니다. 블로그는 1-4의 UserDetailsService로 DB 회원을 사용합니다.
④ LogoutConfigurer::permitAll은 logout(logout -> logout.permitAll())을 줄여 쓴 메서드 참조입니다.

📖 블로그에 적용 — 블로그 화면은 로그인 없이 보기

공식 가이드처럼 requestMatchers(…).permitAll()로 블로그 화면을 열어 두고, 나머지는 로그인이 필요하도록 출입 규칙만 먼저 정해 봅니다.

💡 config/WebSecurityConfig.java — 출입 규칙만 설정
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) {
    return http
            .authorizeHttpRequests(requests -> requests
                    .requestMatchers("/login", "/signup", "/user").permitAll()      // 로그인 · 회원가입
                    .requestMatchers("/", "/articles", "/articles/*", "/js/**", "/error").permitAll()    // 글 목록 · 상세보기 허용
                    .anyRequest().authenticated()                                  // 나머지는 로그인 필요
            )
            .csrf(AbstractHttpConfigurer::disable)   // fetch로 POST/PUT/DELETE 하려면 필요
            .build();
}
📌 확인 누구나 글 목록(/, /articles), 글 상세보기(/articles/* → /articles/1), JS 파일(/js/**), 에러 페이지(/error)를 볼 수 있습니다. 글 등록(/new-article)과 저장 · 수정 · 삭제 API(/api/articles/**)는 anyRequest().authenticated()에 걸려 가입된 회원만 사용할 수 있습니다. *는 한 단계 경로(/articles/1), **는 모든 하위 경로(/articles/1/edit까지)를 뜻합니다. 아직 formLogin을 설정하지 않았으므로 허용하지 않은 주소에 접속하면 로그인 화면 대신 403 Forbidden이 나옵니다. 로그인 화면 연결은 2단원(2-2)에서 추가합니다.

1-3. SecurityFilterChain — 출입 규칙 정하기

📖 HttpSecurity 주요 메서드

메서드하는 일예
authorizeHttpRequestsURL별 출입 규칙 (인가)requestMatchers("/login","/signup").permitAll()
requestMatchers("/admin/**").hasRole("ADMIN")
anyRequest().authenticated()
formLogin로그인 화면 · 성공 후 이동loginPage("/login"), defaultSuccessUrl("/articles", true)
logout로그아웃 처리logoutSuccessUrl("/login"), invalidateHttpSession(true)
exceptionHandling권한 없음(403) 처리accessDeniedPage("/access-denied")
규칙의미
permitAll()누구나 (로그인 안 해도)
authenticated()로그인한 사람만
hasRole("ADMIN")ROLE_ADMIN 권한만 (DB에는 ROLE_ 접두어 붙여 저장)
hasAnyRole("USER","ADMIN")둘 중 하나라도 있으면
⚠️ 규칙 순서 규칙은 위에서부터 먼저 일치하는 것이 적용됩니다. 구체적인 경로(/login, /signup)를 먼저, anyRequest()는 항상 마지막에 둡니다.

1-4. DB 회원으로 로그인하기 — 3총사

📖 시큐리티가 “우리 회원”을 알게 하는 방법

시큐리티는 우리 DB 구조를 모릅니다. 그래서 정해진 인터페이스에 맞춰 회원 정보를 건네줘야 합니다.

구성 요소비유하는 일블로그 코드
UserDetails사원증아이디 · 비밀번호 · 권한을 담은 회원 카드User implements UserDetails
UserDetailsService인사팀 명부 조회아이디(이메일)로 DB에서 회원을 찾아 UserDetails로 반환UserDetailService.loadUserByUsername()
PasswordEncoder지문 대조기가입 시 BCrypt로 암호화 저장, 로그인 시 matches()로 비교BCryptPasswordEncoder 빈
DaoAuthenticationProvider출입 심사관위 두 개(명부 · 대조기)를 이용해 실제 로그인 판정빈 등록 생략 → 부트가 자동 구성
📌 7장 교안과 비교 7장 시큐리티 교안은 Member 엔티티를 CustomUserDetails로 감싸는 방식, 블로그는 User 엔티티가 직접 UserDetails를 구현하는 방식입니다. 역할은 같습니다. UserDetailsService와 PasswordEncoder 빈이 하나씩 있으면 DaoAuthenticationProvider는 스프링 부트가 자동으로 만들어 줍니다.

1-5. 로그인 처리 흐름

📖 로그인 처리 흐름

POST /login (username=이메일, password)→UserDetailService.loadUserByUsername()→BCrypt 비밀번호 비교→세션 생성→/articles 이동

로그인 폼은 Spring Security가 직접 처리하므로 POST /login 컨트롤러는 만들지 않는다. 입력 이름은 반드시 username, password여야 한다.

단계누가무엇을
①브라우저로그인 폼에서 POST /login (username=이메일, password)
②DaoAuthenticationProviderUserDetailService.loadUserByUsername(이메일) 호출 → DB에서 User 조회
③PasswordEncodermatches(입력 비밀번호, DB 암호) 비교
④시큐리티성공 → Authentication을 세션(SecurityContext)에 저장 → /articles 이동
실패 → /login?error
➡️ 다음 단원 개념을 익혔으니 2. 블로그 프로젝트에 시큐리티 적용에서 실제 코드를 작성합니다.

2 블로그 프로젝트에 시큐리티 적용 — 회원가입 · 로그인

🎯 학습목표
  • UserDetails를 구현한 User 엔티티와 UserDetailsService로 DB 회원 로그인을 구현할 수 있다.
  • SecurityFilterChain으로 공개 URL과 인증 필요 URL을 나눌 수 있다.
  • 회원가입(BCrypt 암호화) · 로그인 · 로그아웃 화면을 완성할 수 있다.
📌 준비 1단원 1-2의 build.gradle 의존성(시큐리티 · thymeleaf-extras)을 추가하고 🐘 Load Gradle Changes를 누른 상태에서 시작합니다.

2-1. 회원 엔티티 · Repository · DTO · Service

💡 domain/User.java — UserDetails 구현
@Table(name = "users")   // user는 예약어인 DB가 많아 users 사용
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Getter
@Entity
public class User implements UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id", updatable = false)
    private Long id;

    @Column(name = "email", nullable = false, unique = true)
    private String email;

    @Column(name = "password")
    private String password;

    @Column(name = "name", nullable = false)
    private String name;       // 회원 이름 (화면 표시용)

    @Builder
    public User(String email, String password, String name) {
        this.email = email;
        this.password = password;
        this.name = name;
    }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_USER"));
    }

    @Override public String getUsername() { return email; }   // 이메일을 로그인 ID로
    @Override public String getPassword() { return password; }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return true; }
}
📌 참고 getUsername()이 이메일을 반환하므로 로그인 아이디 = 이메일입니다. getAuthorities()는 모든 회원에게 ROLE_USER를 줍니다. name은 화면에 “[홍길동]님”처럼 보여줄 회원 이름입니다. isAccountNonExpired() 등 4개는 계정 만료 · 잠금 기능을 쓰지 않으므로 모두 true.
⚠️ 기존 users 테이블 ddl-auto: update는 칼럼을 추가만 하고 기존 칼럼 · 제약조건은 바꾸지 않습니다. 예전 실습으로 만든 users 테이블이 이미 있으면 not null 제약조건을 위반 오류가 날 수 있으니, 테스트 데이터만 있다면 Workbench / pgAdmin에서 DROP TABLE users; 후 서버를 재시작해 새로 만드세요.

💡 service/UserDetailService.java · UserService.java
// 로그인 시 Spring Security가 호출 — 이메일로 회원 조회
@RequiredArgsConstructor
@Service
public class UserDetailService implements UserDetailsService {
    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String email) {
        return userRepository.findByEmail(email)
                .orElseThrow(() -> new IllegalArgumentException(email));
    }
}

// 회원가입 — 비밀번호는 반드시 암호화해서 저장
@RequiredArgsConstructor
@Service
public class UserService {
    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public Long save(AddUserRequest dto) {
        return userRepository.save(User.builder()
                .email(dto.getEmail())
                .password(passwordEncoder.encode(dto.getPassword()))
                .name(dto.getName())
                .build()).getId();
    }
}
📌 참고 UserDetailService는 로그인할 때 시큐리티가 부르는 “명부 조회”, UserService는 회원가입 때 비밀번호를 passwordEncoder.encode()로 암호화해 저장합니다. 평문 비밀번호는 절대 DB에 저장하지 않습니다.

2-2. WebSecurityConfig — 보안 설정

💡 config/WebSecurityConfig.java
@Configuration
@EnableWebSecurity
public class WebSecurityConfig {

    // 시큐리티 검사 자체를 건너뛸 경로
    @Bean
    public WebSecurityCustomizer configure() {
        return web -> web.ignoring()
                .requestMatchers("/static/**");
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/login", "/signup", "/user").permitAll()
                        .requestMatchers("/", "/articles", "/articles/*", "/js/**", "/error").permitAll() // 글 목록 · 상세보기 허용
                        .anyRequest().authenticated())        // 나머지는 로그인 필요
                .formLogin(form -> form
                        .loginPage("/login")
                        .defaultSuccessUrl("/articles", true)) // true: 항상 /articles로
                .logout(logout -> logout
                        .logoutSuccessUrl("/login")
                        .invalidateHttpSession(true))
                .csrf(AbstractHttpConfigurer::disable)       // 학습용으로 CSRF 비활성화
                .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
📌 보기는 공개 · 등록은 회원만 글 목록(/, /articles), 상세보기(/articles/*), 정적 JS(/js/**), 에러 페이지(/error)는 로그인 없이 열어 둡니다. 글 등록(/new-article) · 저장/수정/삭제 API(/api/articles/**)는 가입된 회원만 사용할 수 있고, 로그인하지 않았으면 formLogin 설정에 따라 로그인 화면으로 이동합니다. 조회 API까지 공개하려면 permitAll보다 위에 .requestMatchers(HttpMethod.GET, "/api/articles/**").permitAll()을 추가합니다.
📌 참고 WebSecurityCustomizer의 ignoring()은 정적 파일처럼 검사 자체가 필요 없는 경로를 필터 체인에서 제외합니다. csrf().disable()은 학습 편의를 위한 설정으로, 폼에 th:action을 쓰면 CSRF 토큰이 자동으로 들어가므로 실무에서는 켜 두는 것이 원칙입니다.

2-3. 컨트롤러 — 화면 · 회원가입 · 로그아웃

💡 controller/UserApiController.java — 회원가입 처리(POST /user) · 로그아웃
@RequiredArgsConstructor
@Controller
public class UserApiController {
    private final UserService userService;

    @PostMapping("/user")   // signup.html 폼 (name="email", name="password")
    public String signup(AddUserRequest request) {
        userService.save(request);
        return "redirect:/login";
    }

    @GetMapping("/logout")
    public String logout(HttpServletRequest request, HttpServletResponse response) {
        new SecurityContextLogoutHandler().logout(request, response,
                SecurityContextHolder.getContext().getAuthentication());
        return "redirect:/login";
    }
}
📮 Postman으로 회원가입 테스트 POST http://localhost:8080/user → Body 탭에서 x-www-form-urlencoded 선택 → Key/Value에 email, password, name 입력 → Send. 성공하면 redirect:/login을 따라가 로그인 페이지 HTML이 보입니다.
⚠️ raw → JSON으로 보내면 폼 바인딩이 안 되어 값이 모두 null → not-null property … User.email 오류가 납니다.

📖 📮 Postman으로 로그인 테스트

로그인 요청 POST /login은 시큐리티가 처리합니다. 파라미터 이름은 username(이메일), password입니다.

순서설정확인
①POST http://localhost:8080/login → Body: x-www-form-urlencoded → username = test@test.com, password = 1234—
②Postman 요청의 Settings 탭 → Automatically follow redirects 끄기 → Send성공: 302, Headers의 Location: /articles + Set-Cookie: JSESSIONID=…
실패: 302, Location: /login?error
③로그인 성공 후 GET http://localhost:8080/new-article200 — 글 등록 화면 HTML (Postman이 JSESSIONID 쿠키를 자동 저장 · 전송)
④POST /api/articles (raw · JSON, 2강과 동일)201 — 회원만 글 등록 성공
⑤GET http://localhost:8080/logout 후 ③ 다시 Send302 → Location: /login (로그인 필요)
💡 세션 쿠키 로그인 상태는 세션으로 유지됩니다. 서버는 로그인 성공 시 세션을 만들고 그 ID를 JSESSIONID 쿠키로 보내며, 이후 요청에 이 쿠키가 있으면 로그인한 사용자로 인식합니다. Postman 오른쪽 위 Cookies에서 localhost의 JSESSIONID를 확인 · 삭제할 수 있습니다.
🧪 실습

회원가입 → 로그인 → 글 목록

  1. 서버 실행 후 localhost:8080/articles 접속 → 로그인 없이 글 목록 · 상세보기가 보이는지 확인 → 글 등록 버튼 클릭 → 로그인 화면(/login)으로 이동하는지 확인
  2. 회원가입 클릭 → 이메일 · 비밀번호 입력 → 가입하기 → 로그인 화면으로 이동
  3. DB users 테이블에서 비밀번호가 $2a$10$…(BCrypt)로 저장됐는지 확인
  4. 틀린 비밀번호로 로그인 → “이메일 또는 비밀번호가 일치하지 않습니다.” 표시 확인
  5. 올바르게 로그인 → /articles 이동, /logout 접속 → 다시 로그인 화면 (로그인 후에는 글 등록 · 수정 · 삭제 가능)

3 JWT 토큰 (TokenProvider)

🎯 학습목표
  • JWT의 구조(헤더·페이로드·서명)와 발급·검증 과정을 이해한다.
💡 build.gradle — JWT 의존성 추가
dependencies {
    implementation 'io.jsonwebtoken:jjwt:0.9.1'
    implementation 'javax.xml.bind:jaxb-api:2.3.1'   // jjwt 0.9.x는 Java 11+에서 필요
}
💡 application.yaml — 최상위에 JWT 설정 추가
# JWT 설정은 spring: 아래가 아니라 최상위에 둔다 (@ConfigurationProperties("jwt"))
jwt:
  issuer: sudo-blog
  secret_key: ${JWT_SECRET_KEY:study-springboot}
⚠️ 주의 — YAML은 들여쓰기가 곧 구조다. jwt:를 spring.ai 아래에 두면 키가 spring.ai.jwt.*가 되어 JwtProperties에 값이 들어가지 않는다. 키 이름도 필드명과 같아야 한다(issuer).

📖 개념 및 설명

  • 세션 방식: 서버가 로그인 상태를 기억한다. JWT 방식: 서버가 서명한 토큰을 클라이언트가 들고 다니며 매 요청 Authorization: Bearer 토큰으로 보낸다.
  • 토큰 = 헤더.페이로드.서명. 페이로드에 발급자(iss)·발급일(iat)·만료일(exp)·사용자(sub)·id를 담고, 비밀키로 서명해 위조를 막는다.
  • 현재 프로젝트는 토큰 발급·검증 클래스까지 만든 상태다. 요청마다 토큰을 검사하는 필터는 실습 3에서 완성한다.
💡 config/jwt/JwtProperties.java · TokenProvider.java
@Setter
@Getter
@Component
@ConfigurationProperties("jwt")   // application.yaml의 jwt.issuer, jwt.secret_key
public class JwtProperties {
    private String issuer;
    private String secretKey;
}

@RequiredArgsConstructor
@Service
public class TokenProvider {
    private final JwtProperties jwtProperties;

    // 토큰 발급
    public String generateToken(User user, Duration expiredAt) {
        Date now = new Date();
        return Jwts.builder()
                .setHeaderParam(Header.TYPE, Header.JWT_TYPE)
                .setIssuer(jwtProperties.getIssuer())
                .setIssuedAt(now)
                .setExpiration(new Date(now.getTime() + expiredAt.toMillis()))
                .setSubject(user.getEmail())
                .claim("id", user.getId())
                .signWith(SignatureAlgorithm.HS256, jwtProperties.getSecretKey())
                .compact();
    }

    // 유효성 검증 (서명·만료)
    public boolean validToken(String token) {
        try {
            Jwts.parser().setSigningKey(jwtProperties.getSecretKey()).parseClaimsJws(token);
            return true;
        } catch (Exception e) {
            return false;
        }
    }

    // 토큰 → 인증 정보
    public Authentication getAuthentication(String token) {
        Claims claims = getClaims(token);
        Set<SimpleGrantedAuthority> authorities =
                Collections.singleton(new SimpleGrantedAuthority("ROLE_USER"));
        return new UsernamePasswordAuthenticationToken(
                new org.springframework.security.core.userdetails.User(
                        claims.getSubject(), "", authorities), token, authorities);
    }

    public Long getUserId(String token) {
        return getClaims(token).get("id", Long.class);
    }

    private Claims getClaims(String token) {
        return Jwts.parser().setSigningKey(jwtProperties.getSecretKey())
                .parseClaimsJws(token).getBody();
    }
}

6 Render.com 배포 (Docker + PostgreSQL)

🎯 학습목표
  • Dockerfile로 Spring Boot 앱을 컨테이너 이미지로 만들 수 있다.
  • Render PostgreSQL과 Web Service를 연결해 무료로 배포할 수 있다.
  • 무료 배포 환경의 제약(잠자기, 메모리, 파일 저장)을 설명할 수 있다.

📖 왜 Render?

5단원 AWS Elastic Beanstalk는 설정할 것이 많고 요금이 나올 수 있다. Render는 GitHub 저장소만 연결하면 자동으로 빌드·배포해 주고, 무료 Web Service를 제공해 수업 결과물을 공개 URL로 보여 주기 좋다.

DBRDS(MySQL)Render PostgreSQL (같은 대시보드에서 생성)
비용프리 티어 이후 과금무료 (제약 있음)

6-1. GitHub에 업로드

🐙 GitHub 저장소 만들고 push

Render는 GitHub 저장소의 코드를 가져와 빌드한다. 먼저 blogweb(postgresql) 프로젝트를 GitHub에 올린다.

  1. github.com 로그인 → 오른쪽 위 + → New repository
  2. Repository name blogweb-postgresql (괄호는 쓸 수 없다) → Public → README·.gitignore는 추가하지 않음 → Create repository
  3. .gitignore에 아래 두 줄을 추가 (Initializr가 만든 파일에 build/, .idea, out/는 이미 있다)
### 업로드 이미지 · 비밀 정보 ###
uploads/
.env
  1. 터미널에서 아래 명령 실행 (처음 한 번은 GitHub 로그인 창이 뜬다)
# 프로젝트 폴더에서 (IntelliJ 하단 Terminal)

# 이후 수정할 때마다
git add .

💡 확인 — GitHub 저장소 화면에 src, build.gradle, gradlew, Dockerfile이 보이고 build·.idea가 없으면 정상이다.

6-2. Dockerfile 만들기

💡 Dockerfile — 프로젝트 최상위 폴더 (build.gradle 옆)
# ① 빌드 단계: JDK 21로 Gradle 빌드 → 실행 가능한 jar 만들기
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN chmod +x gradlew && ./gradlew clean bootJar -x test --no-daemon

# ② 실행 단계: 가벼운 JRE 21 이미지에 jar만 복사
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar

# 컨테이너에서는 운영(prod) 프로파일로 실행
ENV SPRING_PROFILES_ACTIVE=prod
# 무료 인스턴스 메모리 512MB에 맞춰 자바 힙 제한
ENV JAVA_OPTS="-Xmx300m"

EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
줄의미
FROM ... AS build1단계: JDK가 있는 이미지에서 ./gradlew bootJar로 jar를 만든다 (테스트는 생략 -x test)
FROM eclipse-temurin:21-jre2단계: 실행에 필요한 JRE만 있는 작은 이미지에 jar만 복사 (멀티 스테이지 빌드)
ENV SPRING_PROFILES_ACTIVE=prod컨테이너 안에서는 운영(prod) 설정으로 실행 → Render에 따로 넣지 않아도 된다
-Xmx300m무료 인스턴스 메모리가 512MB라 자바 힙을 제한한다 (메모리 초과로 재시작되는 것 방지)
💡 포트 — Render가 넘겨 주는 PORT는 application.yaml의 server.port: ${PORT:8080}이 받는다. Dockerfile에서 따로 지정하지 않는다.

6-3. application.yaml — 개발(dev) · 운영(prod) 함께 쓰기

💡 src/main/resources/application.yaml — 한 파일에 공통 · dev · prod

---로 문서를 나누고 spring.config.activate.on-profile로 어느 프로파일에서 쓸지 정한다. 맨 위 공통 설정은 항상 적용되고, 실행 중인 프로파일의 설정이 그 위에 덮어써진다.

# =====================================================================
# 공통 설정 — 개발(dev) · 운영(prod) 모두 적용
# =====================================================================
spring:
  application:
    name: blogweb
  profiles:
    default: dev                           # 프로파일을 지정하지 않으면 dev (IntelliJ 실행)

  jpa:
    defer-datasource-initialization: true  # 테이블 생성 후 data.sql 실행
    hibernate:
      ddl-auto: update                     # 테이블 유지, 바뀐 컬럼만 반영 (데이터 유지)
    properties:
      hibernate:
        jdbc:
          time_zone: Asia/Seoul            # created_at 등을 한국 시간으로 저장
    open-in-view: false

  sql:
    init:
      mode: always                         # 시작할 때 data.sql 실행 (중복 방지 SQL)

  datasource:
    driver-class-name: org.postgresql.Driver

server:
  port: ${PORT:8080}                       # Render는 PORT를 넘겨 줌, 로컬은 8080

---
# =====================================================================
# 개발(dev) — 로컬 PostgreSQL, SQL 출력, DevTools
# =====================================================================
spring:
  config:
    activate:
      on-profile: dev

  datasource:
    url: jdbc:postgresql://localhost:5432/springdb
    username: javauser                     # pgAdmin(psql)에서 만든 계정
    password: ${DB_PASSWORD}               # IntelliJ 실행 설정 → Environment variables

  jpa:
    show-sql: true                         # 실행 SQL 출력(학습용)
    properties:
      hibernate:
        format_sql: true

  devtools:
    restart:
      enabled: true                        # 코드 변경 시 서버 자동 재시작
      poll-interval: 2s                    # 변경 확인 간격
      quiet-period: 1s                     # 변경이 멈춘 뒤 재시작까지 대기
      additional-exclude: uploads/**       # 업로드 폴더 변경은 재시작 안 함
    livereload:
      enabled: true                        # 브라우저 자동 새로고침 (포트 35729)

  thymeleaf:
    cache: false                           # 템플릿 수정이 바로 반영

---
# =====================================================================
# 운영(prod) — Render 배포. 접속 정보는 모두 환경변수로
# =====================================================================
spring:
  config:
    activate:
      on-profile: prod

  datasource:
    url: ${DB_URL}                         # jdbc:postgresql://호스트:5432/springdb
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

  jpa:
    show-sql: false                        # 운영에서는 SQL 출력 끔

  thymeleaf:
    cache: true                            # 템플릿 캐시 사용 (성능)
개발 (dev)운영 (prod)
언제IntelliJ에서 실행 (profiles.default: dev)Docker 컨테이너 (ENV SPRING_PROFILES_ACTIVE=prod)
DBlocalhost:5432/springdb, 비밀번호만 환경변수URL · 계정 · 비밀번호 모두 환경변수 (Render PostgreSQL)
SQL 출력켬 (show-sql, format_sql)끔
DevTools · 템플릿 캐시자동 재시작 · 캐시 끔DevTools 없음(jar에서 빠짐) · 캐시 켬
포트8080Render의 PORT
💡 로컬에서 prod 미리 실행해 보기 — IntelliJ 실행 설정 Environment variables에 SPRING_PROFILES_ACTIVE=prod;DB_URL=jdbc:postgresql://localhost:5432/springdb;DB_USERNAME=javauser;DB_PASSWORD=…를 넣으면 운영 설정으로 실행된다. 콘솔에 The following 1 profile is active: "prod"가 보인다.
⚠️ 비밀번호는 파일에 쓰지 않는다 — 모든 비밀 값은 ${...}로만 받는다. GitHub에 올라가도 안전하다.

6-4. Render PostgreSQL 만들기

🐘 Render PostgreSQL (Free)

로컬에서 PostgreSQL로 개발한 blogweb(postgresql) 프로젝트를 배포한다 (1강 3-5: PostgreSQL 드라이버, FROM DUAL 없는 data.sql).

  1. Render 대시보드 → New + → Postgres
  2. Name blogdb, Database springdb, User javauser 입력 → Region Singapore (Web Service와 같은 지역) → Instance Type Free → Create Database
  3. 상태가 Available이 되면 Info → Connections에서 Hostname, Port, Database, Username, Password 확인
Render 환경변수값
DB_URLjdbc:postgresql://Hostname:5432/springdb
DB_USERNAMEjavauser
DB_PASSWORDConnections 화면의 Password
⚠️ URL 형식 주의 — Render가 보여 주는 postgresql://user:pass@host/db는 JDBC 형식이 아니다. 그대로 넣으면 DB에 접속하지 못해 Render Logs에 Driver org.postgresql.Driver claims to not accept jdbcUrl, 이어서 Unable to determine Dialect without JDBC metadata 오류가 나고 앱이 멈춘다. 맨 앞에 jdbc:를 붙이고 호스트 뒤에 :5432를 넣어 jdbc:postgresql://호스트:5432/DB이름으로 바꾸며, 계정·비밀번호는 따로 넣는다.
postgresql://javauser:비밀번호@dpg-xxxx-a/springdb      ← Render 화면 (그대로 X)
jdbc:postgresql://dpg-xxxx-a:5432/springdb              ← DB_URL에 넣을 값
💡 Internal vs External — Web Service와 DB가 같은 Region이면 Internal Hostname(dpg-xxxx-a)으로 빠르게 접속한다. pgAdmin으로 내 PC에서 들여다볼 때는 External Hostname(....singapore-postgres.render.com)을 쓴다.

6-6. 로컬 pgAdmin에서 Render DB 접속하기

🐘 pgAdmin — Register Server

배포된 앱이 쓰는 Render PostgreSQL을 내 PC의 pgAdmin으로 열어 테이블과 데이터를 직접 확인한다. 내 PC에서 접속하므로 Render DB 화면 Info → Connections의 External 정보를 쓴다.

  1. pgAdmin 왼쪽 Servers 마우스 오른쪽 → Register → Server…
  2. General 탭 — Name에 알아보기 쉬운 이름 (예: Render DB(javadb))
  1. Connection 탭 — 아래 표대로 입력하고 Save password?를 켠다
항목값 (Render Connections 화면)
Host name/addressExternal Hostname — dpg-xxxx-a.singapore-postgres.render.com (Internal dpg-xxxx-a는 Render 안에서만 접속됨)
Port5432
Maintenance databaseDatabase 값 — springdb_xxxx (Render가 붙인 접미사까지)
Username / Passwordjavauser / Connections 화면의 Password
  1. Parameters 탭 — SSL mode를 require로 (Render 외부 접속은 SSL 필수)
  1. Advanced 탭 — DB restriction에 springdb_xxxx를 넣으면 이 DB만 목록에 보인다 (선택)
  1. Save → 왼쪽 트리에서 Databases → springdb_xxxx → Schemas → public → Tables → article 확인 → Query Tool에서 select * from article;
⚠️ 접속이 안 될 때
  • could not translate host name: Internal Hostname을 넣었다 → External Hostname 사용
  • SSL/TLS required 또는 no pg_hba.conf entry ... no encryption: Parameters에서 sslmode=require
  • password authentication failed: Render 화면에서 비밀번호를 다시 복사 (앞뒤 공백 주의)
  • Render DB Access Control(허용 IP)에 내 IP가 막혀 있지 않은지 확인 — 기본값은 모든 IP 허용
💡 운영 DB 주의 — 이 서버는 실제 서비스가 쓰는 DB다. DELETE · DROP은 조심하고, 조회 위주로 쓴다. 무료 DB는 만든 지 30일 후 만료된다.

6-7. 무료 플랜 주의사항

⚠️ 알고 쓰기
  • 잠자기: 무료 Web Service는 15분 동안 요청이 없으면 멈추고, 다음 요청 때 다시 켜지느라 약 1분 기다린다. 수업 시연 전에 미리 한 번 접속해 둔다.
  • 메모리 512MB: Spring Boot는 메모리를 많이 쓴다. JAVA_OPTS=-Xmx300m을 지키고, 로그에 Out of memory가 보이면 값을 줄인다.
  • 업로드 이미지: 무료 서비스는 재배포 · 재시작 · 잠들 때마다 uploads/ 폴더 파일이 지워진다. 글은 PostgreSQL에 남고 사진만 깨진다 (아래 💾 참고).
  • 무료 DB 만료: 무료 PostgreSQL은 만든 지 30일이 지나면 만료되고, 유예 기간 뒤 삭제된다. 수업용으로 쓰고 필요하면 새로 만든다.
  • 빌드 시간: 무료 플랜은 한 달 빌드 시간이 정해져 있으므로 작은 수정마다 push하지 말고 모아서 올린다.
💾 업로드 이미지 보관 — Render 파일 시스템은 임시 저장소

Render 서비스의 파일 시스템은 임시(ephemeral)다. 서버에 저장한 파일은 다시 배포되거나, 재시작되거나, 무료 서비스가 잠들 때(15분 미사용) 모두 사라진다. DB(Render PostgreSQL)에 저장한 글은 남으므로, 시간이 지나면 글은 그대로인데 이미지만 404가 된다.

비용무료Starter $7/월부터 + 디스크 용량 요금
코드 변경없음없음 (디스크 연결만)
이미지재배포 · 재시작 · 잠들면 사라짐디스크 경로 아래 파일은 계속 유지
추천수업 시연, 과제 제출 화면 확인실제로 계속 운영할 서비스

① 무료로 시연할 때

  • 시연 직전에 글과 이미지를 새로 등록하고 바로 보여 준다.
  • 예전에 올린 이미지가 깨져 보이면 정상이다 (서버가 다시 켜지면서 파일이 지워진 것). 이미지 없이 글만 남은 상태가 된다.

② 유료 + Persistent Disk로 보관할 때

  1. Web Service → Settings → Instance Type → Edit에서 Free 대신 유료 플랜 선택 (디스크는 유료 인스턴스에서만 연결 가능)

  2. Web Service → Disks → Add Disk
  3. Mount Path: /app/uploads — Dockerfile의 WORKDIR /app + app.upload-dir 기본값 uploads

💡 코드는 그대로 — LocalFileStorageService가 /app/uploads에 저장하고, WebMvcConfig가 같은 폴더를 /uploads/**로 보여 준다. 디스크가 그 폴더에 붙기만 하면 파일이 유지된다. Mount Path 아래에 쓴 파일만 남는다는 점에 주의한다.
⚠️ 디스크를 붙이면 — 재배포할 때 기존 서버를 먼저 멈추고 새 서버를 켜므로 잠깐 접속이 끊긴다(무중단 배포 불가). 서버를 여러 대로 늘릴 수도 없다. 디스크는 24시간마다 자동 스냅샷이 만들어진다.
