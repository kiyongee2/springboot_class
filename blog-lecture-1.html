⚙️ Lombok 설정 (IntelliJ)

Lombok은 getter·생성자·빌더 같은 반복 코드를 애너테이션 하나로 컴파일할 때 자동 생성해 주는 라이브러리다. Initializr에서 Lombok을 골랐다면 build.gradle에 아래 의존성이 이미 들어 있다.

dependencies {
    compileOnly 'org.projectlombok:lombok'          // 컴파일할 때만 사용
    annotationProcessor 'org.projectlombok:lombok'  // 애너테이션을 읽어 코드 생성
    testCompileOnly 'org.projectlombok:lombok'
    testAnnotationProcessor 'org.projectlombok:lombok'
}
  1. Settings → Plugins → Installed → Lombok 플러그인이 켜져 있는지 확인 (IntelliJ에 기본 포함, 없으면 Marketplace에서 설치)
  2. Settings → Build, Execution, Deployment → Compiler → Annotation Processors → Enable annotation processing 체크 (Default, Gradle Imported 프로필 모두)
  3. 프로젝트를 처음 열 때 오른쪽 아래에 "Lombok requires enabled annotation processing" 알림이 뜨면 Enable 클릭으로도 된다
  4. Build → Rebuild Project 한 번 실행
애너테이션만들어 주는 코드이 프로젝트에서 쓰는 곳
@Getter모든 필드의 getXxx()Article, DTO
@NoArgsConstructor매개변수 없는 기본 생성자 (JPA·JSON 변환에 필요)Article(access = PROTECTED), AddArticleRequest
@AllArgsConstructor모든 필드를 받는 생성자AddArticleRequest
@BuilderArticle.builder().title(..).build() 빌더 패턴Article 생성자
@RequiredArgsConstructorfinal 필드를 받는 생성자 → 생성자 주입(DI)Service, Controller
💡 확인 방법 — Article 클래스를 열고 Structure 창(Alt+7)을 보면 직접 쓰지 않은 getTitle() 등이 보인다. 다른 클래스에서 article.get을 입력하면 자동 완성 목록에 나온다.
⚠️ 자주 나는 오류 — cannot find symbol: method getTitle() / variable log: Annotation processing이 꺼져 있거나 annotationProcessor 의존성이 빠졌다. No default constructor for entity: 엔티티에 @NoArgsConstructor가 없다.
⚙️ 서버 자동 재시작 — DevTools (IntelliJ Community)

Community 버전에는 Spring Boot 실행 설정의 "코드 변경 시 갱신" 옵션이 없다. DevTools를 추가하고 IntelliJ가 자동으로 빌드하도록 설정하면, 코드를 고칠 때마다 서버가 1~2초 안에 다시 시작된다.

  1. Initializr에서 Spring Boot DevTools를 선택했다면 build.gradle에 developmentOnly 'org.springframework.boot:spring-boot-devtools'가 이미 들어 있다. 없으면 직접 추가 → Gradle 창 🔄 Reload
  2. Settings → Build, Execution, Deployment → Build Tools → Gradle → Build and run using, Run tests using를 IntelliJ IDEA로 변경
  3. 위의 ⚙️ Lombok 설정에서 Enable annotation processing을 켰는지 확인 (IntelliJ로 빌드하면 꼭 필요)
  4. Settings → Build, Execution, Deployment → Compiler → Build project automatically 체크
  5. Settings → Advanced Settings → Allow auto-make to start even if developed application is currently running 체크
  6. 서버를 정지(■)했다가 main 옆 ▶로 다시 실행

application.yaml — DevTools 설정 (선택)

DevTools는 추가만 해도 기본값으로 동작한다. 재시작 간격이나 자동 새로고침을 조정하고 싶을 때 spring: 아래에 넣는다.

spring:
  devtools:
    restart:
      enabled: true                     # 코드 변경 시 서버 자동 재시작 (기본값 true)
      poll-interval: 2s                    # 변경 확인 간격
      quiet-period: 1s                     # 변경이 멈춘 뒤 재시작까지 대기
      additional-exclude: uploads/**       # 업로드 폴더 변경은 재시작 안 함
    livereload:
      enabled: true                     # 브라우저 자동 새로고침 (포트 35729)
  thymeleaf:
    cache: false                      # 템플릿 수정이 바로 반영 (DevTools가 자동 설정)
기능동작
Restartbuild/(또는 out/)의 class 파일이 바뀌면 서버를 다시 시작한다. static/, templates/ 변경은 재시작 없이 바로 반영된다.
LiveReload서버가 다시 시작되면 브라우저를 자동 새로고침한다. Chrome 웹 스토어의 LiveReload 확장 프로그램을 설치하고 탭에서 켠다.
개발용 기본값Thymeleaf 캐시 끄기 등 개발에 편한 설정을 자동 적용한다. java -jar로 실행하는 운영 환경에서는 DevTools가 꺼진다.
💡 확인 방법 — HomeController의 문자열을 바꾸고 2~3초 기다리면 콘솔에 restartedMain 로그가 다시 찍힌다. 브라우저만 새로고침하면 바뀐 문구가 보인다. 자동 빌드가 안 되면 Ctrl+F9(Build Project)를 눌러도 재시작된다.
⚠️ 주의 — MySQL은 서버가 재시작돼도 데이터가 그대로 남는다 (ddl-auto: update 기준). Postman으로 등록한 글도 유지된다.

2-2. application.yaml & data.sql

🎯 학습목표
  • JPA 옵션과 MySQL 접속 정보를 설정할 수 있다.
  • ddl-auto 값에 따라 테이블과 데이터가 어떻게 되는지 설명할 수 있다.
  • data.sql로 샘플 데이터를 중복 없이 넣을 수 있다.

📖 개념 및 설명

설정의미
jpa.show-sql · format_sqlJPA가 만든 SQL을 콘솔에 보기 좋게 출력한다. 학습할 때 어떤 쿼리가 나가는지 확인하는 용도.
hibernate.ddl-auto: update엔티티를 보고 없는 테이블·컬럼만 만든다. 기존 데이터는 지우지 않는다.
defer-datasource-initialization: trueHibernate가 테이블을 만든 뒤에 data.sql을 실행한다. 없으면 테이블이 없어 INSERT가 실패한다.
sql.init.modealways면 시작할 때마다 data.sql을 실행한다. 그래서 data.sql은 여러 번 실행돼도 중복되지 않게 작성한다. 테이블을 만드는 엔티티가 아직 없으므로 4단원 전까지는 never로 둔다.
open-in-view: falseDB 연결을 화면(View)까지 열어 두지 않는다. 필요한 데이터는 Service에서 DTO로 모두 꺼내 둔다.
datasourceMySQL 접속 정보. 3단원에서 만드는 springdb DB와 javauser 계정을 쓴다. 비밀번호는 환경변수로 넣는다.

📖 ddl-auto — 테이블을 어떻게 다룰까?

ddl-auto시작할 때종료할 때데이터쓰는 곳
create-drop테이블 삭제 후 생성테이블 삭제사라짐테스트
create테이블 삭제 후 생성그대로사라짐테이블 구조를 처음부터 다시 만들 때
update엔티티와 비교해 없는 컬럼만 추가그대로유지로컬 개발 (이 교안)
validate엔티티와 테이블이 맞는지 검사만그대로유지운영
none아무것도 안 함그대로유지운영 (스키마를 SQL로 관리)
💡 src/main/resources/application.yaml
spring:
  application:
    name: blogweb                       # 애플리케이션 이름

  jpa:
    show-sql: true                      # 실행되는 SQL을 콘솔에 출력 (학습용)
    defer-datasource-initialization: true  # 테이블 생성 뒤에 data.sql 실행
    hibernate:
      ddl-auto: update                  # 테이블 유지, 바뀐 컬럼만 반영
    properties:
      hibernate:
        format_sql: true                # SQL을 줄바꿈해 보기 좋게 출력
    open-in-view: false                 # DB 연결을 Service 계층까지만 사용

  sql:
    init:
      mode: never                       # 4단원(Article 엔티티) 후 always로 변경

  datasource:
    url: jdbc:mysql://localhost:3306/springdb?serverTimezone=Asia/Seoul&characterEncoding=UTF-8
    username: javauser                  # 3단원에서 만든 계정
    password: ${DB_PASSWORD:본인비밀번호}     # 환경변수 DB_PASSWORD 우선
    driver-class-name: com.mysql.cj.jdbc.Driver
💡 MySQL Workbench로 확인 — 4단원까지 마친 뒤 javauser로 접속 (4단원 끝 ▶ 참고) → SELECT * FROM springdb.article; 실행 → 샘플 글 3개를 확인한다.
⚠️ 실행 순서 주의 — data.sql은 article 테이블에 INSERT한다. 4단원에서 Article 엔티티를 만들기 전에 always로 실행하면 Table 'springdb.article' doesn't exist 오류로 앱이 시작되지 않는다. 그래서 위 yaml은 never로 두었다가, 엔티티를 만든 뒤 always로 바꾼다.
💡 나중에 추가 — Spring AI(spring.ai.google.genai)와 JWT(jwt) 설정은 2강 4단원 · 3강 2단원에서 이 파일에 이어서 추가한다.
💡 src/main/resources/data.sql — 샘플 글 3개 (중복 방지)
-- 같은 제목의 글이 없을 때만 넣는다 → 서버를 여러 번 재시작해도 3개만 유지
INSERT INTO article (title, content, image_url, created_at, updated_at)
SELECT '제목 1 입니다.', '내용 1 입니다.', NULL, NOW(), NOW()
FROM DUAL WHERE NOT EXISTS (SELECT 1 FROM article WHERE title = '제목 1 입니다.');

INSERT INTO article (title, content, image_url, created_at, updated_at)
SELECT '제목 2 입니다.', '내용 2 입니다.', NULL, NOW(), NOW()
FROM DUAL WHERE NOT EXISTS (SELECT 1 FROM article WHERE title = '제목 2 입니다.');

INSERT INTO article (title, content, image_url, created_at, updated_at)
SELECT '제목 3 입니다.', '내용 3 입니다.', NULL, NOW(), NOW()
FROM DUAL WHERE NOT EXISTS (SELECT 1 FROM article WHERE title = '제목 3 입니다.');
⚠️ 왜 INSERT ... VALUES를 쓰지 않을까? — MySQL은 서버를 꺼도 데이터가 남는다. 단순 INSERT ... VALUES를 mode: always로 실행하면 재시작할 때마다 샘플 글이 3개씩 늘어난다. WHERE NOT EXISTS로 이미 있는 글은 건너뛴다.

3-1. MySQL 설치

🐬 MySQL 설치

이 교안은 로컬에서도 MySQL을 사용한다. 서버를 다시 시작해도 데이터가 남고, 운영(AWS RDS)과 같은 DB라 배포할 때 바꿀 것이 적다.

  1. MySQL Community Server 8.x 설치 (Windows: MySQL Installer) → root 비밀번호 설정, 포트 3306
  2. 접속·관리 도구 MySQL Workbench 설치 (Installer에 포함)
💡 Docker를 쓴다면 — 설치 대신 컨테이너 하나로 준비할 수 있다. 이 명령은 아래 SQL(계정·DB 생성)까지 한 번에 해 준다.

4 Article 엔티티 (@Entity)

🎯 학습목표
  • @Entity로 클래스를 테이블과 매핑하고, 생성·수정 시각을 자동으로 기록할 수 있다.
  • 빌더 패턴과 의미 있는 변경 메서드(update())로 객체를 다룬다.

📖 개념 및 설명

  • @NoArgsConstructor(access = PROTECTED) — JPA가 쓰는 기본 생성자를 만들되, 외부에서 함부로 new Article() 하지 못하게 막는다.
  • @Builder — Article.builder().title(..).content(..).build() 형태로 읽기 쉽게 생성한다.
  • @CreatedDate / @LastModifiedDate + AuditingEntityListener — 저장·수정 시각 자동 기록 (메인 클래스의 @EnableJpaAuditing 필요)
  • Setter 대신 update() 메서드로만 값을 바꾼다 → 변경 지점이 한곳에 모인다.
💡 domain/Article.java
package com.sudo.blogweb.domain;

@EntityListeners(AuditingEntityListener.class)
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Getter
@Entity
public class Article {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // PK 자동 증가
    @Column(name = "id", updatable = false)
    private Long id;

    @Column(name = "title", nullable = false)
    private String title;

    @Column(name = "content", nullable = false, columnDefinition = "TEXT")   // 긴 본문 (VARCHAR(255) 초과 방지)
    private String content;

    @Column(name = "image_url")
    private String imageUrl;          // 업로드한 이미지 경로 (/uploads/xxx.jpg)

    @CreatedDate
    @Column(name = "created_at")
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    @Builder   // 빌더 패턴으로 객체 생성
    public Article(String title, String content, String imageUrl) {
        this.title = title;
        this.content = content;
        this.imageUrl = imageUrl;
    }

    // 요청 받은 값으로 수정 (트랜잭션 안에서 호출 → 자동 UPDATE)
    public void update(String title, String content, String imageUrl) {
        this.title = title;
        this.content = content;
        this.imageUrl = imageUrl;
    }
}
⚠️ MySQL에서 String 컬럼 길이 — JPA는 String을 기본 VARCHAR(255)로 만든다. 본문이 255자를 넘으면 Data too long for column 'content' 오류가 난다. 긴 글은 columnDefinition = "TEXT"로 지정한다. 이미 테이블이 만들어졌다면 update는 컬럼 타입을 바꾸지 않으므로 Workbench에서 ALTER TABLE article MODIFY content TEXT NOT NULL;을 실행한다.
💡 BlogwebApplication.java — JPA Auditing 켜기 (메인 클래스에 애너테이션 추가)

@SpringBootApplication
public class BlogwebApplication {
    public static void main(String[] args) {
        SpringApplication.run(BlogwebApplication.class, args);
    }
}

6 DTO (요청 · 응답 데이터)

🎯 학습목표
  • 엔티티를 그대로 노출하지 않고 용도별 DTO로 나누는 이유를 설명할 수 있다.

📖 개념 및 설명

클라이언트가 보낸 JSON은 요청 DTO로 받고, 화면·API에 필요한 값만 응답 DTO에 담아 돌려준다. 엔티티가 바뀌어도 API 형식이 흔들리지 않는다.

💡 dto/AddArticleRequest.java — DTO → 엔티티 변환
@NoArgsConstructor
@AllArgsConstructor
@Getter
public class AddArticleRequest {
    private String title;
    private String content;
    private String imageUrl;

    // DTO를 엔티티로 만들어 주는 메서드
    public Article toEntity() {
        return Article.builder()
                .title(title)
                .content(content)
                .imageUrl(imageUrl)
                .build();
    }
}
💡 dto/UpdateArticleRequest.java — 글 수정 요청
@NoArgsConstructor
@AllArgsConstructor
@Getter
public class UpdateArticleRequest {
    private String title;
    private String content;
    private String imageUrl;
}
💡 toEntity()가 없는 이유 — 수정은 새 엔티티를 만드는 것이 아니라, DB에서 꺼낸 기존 Article의 update(title, content, imageUrl)를 호출해 값만 바꾼다 (7단원 BlogService.update()). @Transactional 안에서 바뀐 값은 자동으로 UPDATE된다.

7 BlogService (업무 로직)

🎯 학습목표
  • 업무 로직을 Service에 모으고, @Transactional과 더티 체킹으로 수정을 처리한다.

📖 개념 및 설명

  • @RequiredArgsConstructor — final 필드를 받는 생성자를 Lombok이 만들어 생성자 주입이 된다.
  • 더티 체킹(dirty checking) — 트랜잭션 안에서 조회한 엔티티의 값을 바꾸면, 끝날 때 JPA가 변경을 감지해 UPDATE를 자동 실행한다. save()를 다시 부를 필요가 없다.
  • 없는 id를 조회하면 IllegalArgumentException("not found: id")를 던진다.
💡 service/BlogService.java
@RequiredArgsConstructor   // final 필드 생성자 주입
@Service
public class BlogService {
    private final BlogRepository blogRepository;

    // 글 추가
    public Article save(AddArticleRequest request) {
        return blogRepository.save(request.toEntity());
    }

    // 전체 글 조회
    public List<Article> findAll() {
        return blogRepository.findAll();
    }

    // 글 1건 조회
    public Article findById(long id) {
        return blogRepository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("not found: " + id));
    }

    // 글 삭제
    public void delete(long id) {
        blogRepository.deleteById(id);
    }

    // 글 수정 — 트랜잭션 종료 시 변경 내용 자동 반영
    @Transactional
    public Article update(long id, UpdateArticleRequest request) {
        Article article = blogRepository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("not found: " + id));
        article.update(request.getTitle(), request.getContent(), request.getImageUrl());
        return article;
    }
}

8 BlogApiController (REST)

🎯 학습목표
  • HTTP 메서드별 매핑 애너테이션과 ResponseEntity로 상태코드를 지정해 응답할 수 있다.

📖 개념 및 설명

  • @RestController = @Controller + @ResponseBody → 반환 객체를 JSON으로 변환한다.
  • @RequestBody는 JSON 본문을 DTO로, @PathVariable은 URL의 {id}를 변수로 받는다.
  • ResponseEntity.status(HttpStatus.CREATED)로 등록 성공 시 201을 돌려준다.
💡 controller/BlogApiController.java
@RequiredArgsConstructor
@RestController   // 객체를 JSON으로 반환
public class BlogApiController {
    private final BlogService blogService;

    // 글 등록 → POST /api/articles
    @PostMapping("/api/articles")
    public ResponseEntity<Article> addArticle(@RequestBody AddArticleRequest request) {
        Article savedArticle = blogService.save(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(savedArticle);
    }

    // 글 목록 → GET /api/articles
    @GetMapping("/api/articles")
    public ResponseEntity<List<ArticleResponse>> findAllArticles() {
        List<ArticleResponse> articles = blogService.findAll()
                .stream()
                .map(ArticleResponse::new)
                .toList();
        return ResponseEntity.ok().body(articles);
    }

    // 글 조회 → GET /api/articles/1
    @GetMapping("/api/articles/{id}")
    public ResponseEntity<ArticleResponse> findArticle(@PathVariable long id) {
        return ResponseEntity.ok().body(new ArticleResponse(blogService.findById(id)));
    }

    // 글 삭제 → DELETE /api/articles/1
    @DeleteMapping("/api/articles/{id}")
    public ResponseEntity<Void> deleteArticle(@PathVariable long id) {
        blogService.delete(id);
        return ResponseEntity.ok().build();
    }

    // 글 수정 → PUT /api/articles/1
    @PutMapping("/api/articles/{id}")
    public ResponseEntity<Article> updateArticle(@PathVariable Long id,
                                                 @RequestBody UpdateArticleRequest request) {
        return ResponseEntity.ok().body(blogService.update(id, request));
    }

    // AI 글쓰기 제안 → POST /api/ai-suggestions
    @PostMapping("/api/ai-suggestions")
    public ResponseEntity<WritingSuggestionResponse> writingAssist(
            @RequestBody WritingSuggestionRequest request) {
        return ResponseEntity.ok().body(writingAssistantService.getWritingAssist(request));
    }
}
